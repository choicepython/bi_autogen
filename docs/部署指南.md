# BI AutoGen 部署指南

本指南面向需要从零部署 `bi_autogen` 项目的高级开发者。覆盖环境准备、依赖安装、配置、数据库初始化、启动方式、日志、可观测性、优雅关闭与健康检查。

> 项目位置：`D:\zhiwen\bi_autogen`
> 项目类型：基于 AutoGen SDK 的 BI 数据分析智能体（Python 3.12+）
> 依赖管理：`uv`

---

## 1. 环境要求

部署前需准备以下运行环境与外部服务。

| 组件 | 版本要求 | 用途 |
|---|---|---|
| Python | 3.12+ | 运行时 |
| PostgreSQL | 14+（需启用 `pgcrypto` 扩展） | 持久化会话/路由/Agent/工具/LLM 调用记录、数据快照、用户反馈 |
| Elasticsearch | 7.10.2 | 动态 API schema 召回、业务 skills 检索、上下文发现 |
| `uv` | 最新版 | 依赖管理与虚拟环境 |
| LLM API | Qwen3 兼容 OpenAI 接口 | 主模型 + 路由意图分类选择器模型 |
| Playwright 内核 | 由 `playwright` 包自动管理 | pyecharts 图表截图渲染 |
| 网络 | 能访问 LLM、API 网关、ES、PostgreSQL | 同上 |

**网络访问要求**

- LLM API：必须可达（路由层、Agent 推理、语义缓存嵌入均依赖）
- API 网关：`BI_API_GATEWAY_URL` 指向的业务 API 入口
- ES：`BI_ES_HOSTS` 指向的 Elasticsearch 集群
- PostgreSQL：`BI_DB_HOST:BI_DB_PORT`

> 注意：ES 强制使用 7.x 客户端（`elasticsearch7>=7.10.0,<8.0.0`），与 ES 8.x 不兼容。

**安装 `uv`（如未安装）**

```bash
# Linux / macOS
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows PowerShell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

**安装 Playwright 内核（图表渲染需要）**

```bash
uv run playwright install chromium
```

### 3.19 优雅降级配置

系统在多个依赖缺失时支持自动降级，确保核心功能可用。启动时通过 `startup_check` 打印所有依赖状态（`configured` / `degraded` / `disabled`），便于运维快速定位降级项。

| 依赖 | 缺失时降级行为 | 相关配置 |
|---|---|---|
| Elasticsearch | 自动降级为本地 jieba 中文分词搜索，从 `source/*.jsonl` 加载知识源 | `BI_ES_HOSTS` 为空 + `jieba` 已安装 |
| ES 资源索引 | `ensure_index_exists()` 启动时自动根据 `db/es_schema/` schema 创建索引 | `BI_ES_RESOURCE_INDEX` 索引不存在时自动创建 |
| Redis | `store_factory` 选择 `InMemoryConversationStore` / `InMemoryDataContextCache`，会话与 DataContext 不跨进程持久化 | `BI_REDIS_URL` 为空 |
| Langfuse | LLM 可观测性降级为 no-op（不发送 trace），不影响主流程 | `BI_LANGFUSE_HOST` / 公钥 / 密钥 任一为空 |
| PostgreSQL | DB 写入指数退避跳过，TraceRecorder 仍写本地 JSONL 文件 | `BI_DB_HOST` 不可达 |
| 搜索工具（百度千帆） | RAGAgent 降级为纯知识回答模式（`_NO_TOOL_BEHAVIOR`），仅依赖 LLM 自身知识 | `BI_WEB_SEARCH_URL` 或 `BI_WEB_SEARCH_API_KEY` 为空 |
| 知识检索（内部） | 同上，未配置 URL 的搜索工具不注册 | `BI_SEARCH_KNOWLEDGE_URL` 为空 |

**启动检查输出示例**（`startup_check`）：

```

[startup_check] Elasticsearch          : configured
[startup_check] ES 资源索引            : configured (ensure_index_exists 已检查/创建)
[startup_check] PostgreSQL             : degraded (connection refused, 跳过 DB 写入)
[startup_check] Redis                  : disabled (BI_REDIS_URL 为空, 使用 InMemory)
[startup_check] Langfuse               : disabled (未配置, no-op)
[startup_check] 搜索工具-知识检索       : configured

[startup_check] jieba 分词              : configured (ES 降级方案可用)
```

## 6. 启动方式

`main.py` 提供 4 种运行模式，通过 CLI 参数选择。

> **启动检查**：所有模式启动时均会执行 `startup_check`，逐项探测 LLM、ES、PostgreSQL、Redis、Langfuse、搜索工具、jieba 分词等依赖的可达性，并打印 `configured` / `degraded` / `disabled` 状态。运维可据此快速确认哪些功能处于降级模式（详见 [§3.19 优雅降级配置](#319-优雅降级配置)）。

### 6.1 交互模式（默认）

```bash
uv run python main.py
```

- 启动 REPL，提示符 `你: `，输入查询后流式打印事件
- 同一进程内保持 `session_id` 不变（基于启动时间戳），支持多轮对话上下文
- 输入 `quit` / `exit` / `q` 退出；Ctrl+C / EOF 也可退出
- 每轮结束后输出 `TraceRecorder` 文本摘要（任务、耗时、trace 文件路径）
- 事件以人类可读格式打印（`[会话开始]`、`[规划中...]`、`[Agent名] 开始执行...`、表格预览等）

### 6.2 单任务模式

```bash
uv run python main.py 查询本月生产产出数据
```

- 一次性执行单个查询，打印完整流式事件后退出
- 适合脚本调用 / CI 验证
- 多个参数会用空格拼接为完整 query

### 6.3 SSE 单任务模式

```bash
uv run python main.py --sse 查询本月生产产出数据
```

- 输出标准 SSE 文本流（`data: {...}\n\n`）到 stdout
- 用于对接下游 SSE 消费方（非 HTTP 路径）
- 出错时仍会输出 `ERROR` 类型的 SSE 事件并以 `exit 1` 退出

### 6.4 FastAPI 服务模式

```bash
uv run python main.py --serve
```

- 启动 `uvicorn` + FastAPI 应用（`gateway/app.py:create_app()`）
- 监听 `BI_SERVER_HOST:BI_SERVER_PORT`（默认 `0.0.0.0:8000`）
- 应用生命周期 `lifespan`：
  - 启动：`init_db()` 建表（失败则跳过 DB 写入，继续运行）→ `ensure_index_exists()` 检查/创建 ES 资源索引 → `db_writer.start()` 启动后台批量写入
  - 关闭：`db_writer.stop()` → `BITeam.shutdown()` 优雅关闭 → `close_pool()` 关闭连接池
- 默认挂载前端静态页面 `gateway/static/` 到根路径 `/`

| 端点 | 方法 | 用途 |
|---|---|---|
| `/api/v1/chat` | POST | Web SSE 聊天主入口 |
| `/api/v1/health` | GET | 健康检查 |
| `/api/v1/metrics/agents` | GET | Agent 成功率/耗时/Token |
| `/api/v1/metrics/tools` | GET | 工具调用频次/错误率 |
| `/api/v1/metrics/sessions` | GET | 会话按小时统计 |
| `/api/v1/metrics/routing` | GET | 路由层命中分布 + Agent 分布 |
| `/api/v1/sessions/{session_id}` | GET | 会话完整链路追溯 |
| `/api/v1/feedback` | POST | 用户反馈提交 |

中间件链（后添加先执行）：`RequestLogMiddleware` → `RateLimitMiddleware`（默认 `max_concurrent=20`）→ `CORSMiddleware`（仅 `BI_CORS_ORIGINS` 非空时挂载）。

> 并发限制：`RateLimitMiddleware` 限制全局并发 20，单机部署需评估是否足够。

## 7. 日志体系

日志初始化在 `main.py:_setup_logging()`，**模块导入时即自动执行**（无需手动调用）。

### 7.1 日志目录与文件

日志根目录：`log/`（项目根下，由 `_LOG_DIR` 决定）。

| 文件 | logger 范围 | 用途 |
|---|---|---|
| `log/app.log` | 根 logger（除被拦截的） | 通用应用运行日志 |
| `log/llm.log` | `bi_autogen.llm_trace` | 每次 LLM 调用的简要摘要（不含完整 request/response） |
| `log/trace.log` | `bi_autogen.trace` | Agent 动作轨迹（路由、规划、工具调用） |
| `log/llm/llm_YYYY-MM-DD.jsonl` | LLM JSONL 文件 | **每日一个文件**，记录 LLM 请求/响应的完整 JSON |
| `log/trace/{sid}_YYYYMMDD_HHMMSS.jsonl` | TraceRecorder 写入 | 每次任务一个文件，前 8 位 session_id 防冲突 |

### 7.2 轮转策略

- 文件 handler 使用 `TimedRotatingFileHandler`，**按日午夜轮转**
- `backupCount=30`，保留 **30 天**历史
- 文件后缀 `.%Y-%m-%d.log`（如 `app.log.2026-07-28.log`）
- 编码统一 UTF-8

### 7.3 Unicode 解码过滤器

`_UnicodeLogFilter`（`main.py`）：

- 将日志消息中的 `\uXXXX` 转义序列还原为中文字符，避免 `\u4e2d\u6587` 这种不可读形式
- 先尝试 JSON 反序列化（处理 `json.dumps(..., ensure_ascii=True)` 产生的字符串）
- 失败则用正则 `\u([0-9a-fA-F]{4})` 逐字符替换
- 同时处理 `record.args` 中的字符串参数
- 对非字符串的 `record.msg` 先 `str()` 化再解码（如 AutoGen Event 对象）
- 同时挂在 console + 各 file handler，确保终端也显示中文

### 7.4 第三方库日志抑制

以下 logger 被强制设为 `WARNING` 级别，避免 INFO 噪音：

- `httpx`
- `autogen_core`
- `autogen_agentchat`
- `autogen_ext`
- `openai`

### 7.5 日志格式

```
%(asctime)s [%(levelname)s] %(name)s:%(lineno)d: %(message)s
```

示例：

```
2026-07-28 10:23:45,123 [INFO] bi_autogen.llm_trace:312: [APIAgent] #1 LLM请求 → 5条消息, 2个工具
```

### 7.6 日志分类与传播

- `bi_autogen.llm_trace`：`propagate=False`，只写到 `llm.log` + console，**不**进 `app.log`，避免重复
- `bi_autogen.trace`：`propagate=False`，只写到 `trace.log` + console
- 其他所有 logger（含第三方）→ 根 logger → `app.log` + console

### 7.7 LLM JSONL 日志格式

由 `observability/logging_client.py:_write_llm_log()` 实时追加写入（`flush` 每行）。字段示例：

```json
{
  "session_id": "20260728_102345",
  "chat_id": "chat_001",
  "call_index": 1,
  "agent": "APIAgent",
  "timestamp": "2026-07-28T10:23:45.123456",
  "direction": "request",
  "message_count": 5,
  "tool_count": 2,
  "messages": [{"role": "system", "content": "..."}, {"role": "user", "source": "user", "content": "..."}],
  "tools": [{"name": "api_query", "description": "..."}],
  "request_body": {"model": "qwen3-32b", "temperature": 0.7, "stream": true, "extra_body": {...}}
}
```

- 每次调用产生 2 行：`direction=request` 和 `direction=response`
- 异常时产生 1 行 `direction=error`，含 `error_type`（`TimeoutError` / 异常类名）和 `error_message`
- 流式调用额外含 `stream: true`、`chunk_count`
- 响应行含 `finish_reason`、`usage.prompt_tokens`、`usage.completion_tokens`、`cached`、`thought`（思考链）

## 8. 可观测性

### 8.1 TraceRecorder（`observability/trace.py`）

记录单次任务执行的全链路事件，每步实时 flush 到 JSONL 文件。

**记录的事件类型：**

| 事件 | 方法 | 内容 |
|---|---|---|
| `header` | 构造函数 | task、started_at、session_id、chat_id |
| `routing` | `record_routing()` | layer（1/2/3）、mode（single_agent/full_team）、agent_type、reasoning、api_meta_count、skills_count、duration_ms |
| `plan_output` | `record_plan_output()` | PlanAgent 输出的完整 DAG（`tasks` 列表） |
| `tool_call` | `record_tool_call()` | agent_name、tool_name、arguments、result（截断到 3000 字符） |
| `footer` | `finish()` | finished_at、duration_seconds、total_steps、stop_reason |

**特性：**

- 文件命名：`{session_id前8位}_{开始时间}.jsonl`，避免同日多 session 覆盖
- 每行 JSON 都带 `session_id` 和 `chat_id`，便于检索
- 通过 ContextVar `_trace_recorder_var` 暴露给 Agent 的 `on_after_turn` 钩子
- `to_text_summary()` 返回人类可读摘要，CLI 模式下每轮结束后打印

### 8.2 LoggingChatCompletionClient（`observability/logging_client.py`）

包装真实 `ChatCompletionClient`（`OpenAIChatCompletionClient`），在 `create()` 和 `create_stream()` 前后插入日志与 DB 写入。

**职责：**

1. **JSONL 日志**：每次 LLM 调用前后通过 `_write_llm_log()` 实时写入 `log/llm/llm_YYYY-MM-DD.jsonl`
2. **DB 记录**：通过 `db_writer.enqueue_llm_call()` 异步写入 `llm_call` 表（请求和响应各一条）
3. **请求超时**：用 `asyncio.wait_for()` 包裹内部调用，超时为 `BI_LLM_REQUEST_TIMEOUT`
4. **思考模式注入**：根据 `_enable_thinking_var` 合并 `extra_body.chat_template_kwargs.enable_thinking`，覆盖请求级偏好
5. **错误捕获**：超时或异常时写入 `direction=error` 行，再 re-raise

**关键设计：**

- 请求日志在**调用前**写入，确保异常时请求不丢失
- `_resolve_agent_name()` 优先用 ContextVar 中的 `agent_name`，回退到 messages 中最后一条 `AssistantMessage.source`，兜底 `?`
- `call_index` 在单 session 内自增，由 `_next_call_index()` 维护
- Qwen3 兼容 patch：`_patch_qwen3_reasoning()` 在模块加载时执行，将响应中的 `reasoning` 字段复制到 `model_extra["reasoning_content"]`（AutoGen 只识别后者）

### 8.3 ContextVar 系统

`observability/logging_client.py` 定义以下 ContextVar，支持并发隔离：

| ContextVar | 设置入口 | 用途 |
|---|---|---|
| `session_id` | `set_session_id()`（DispatchLayer.run 调用） | 当前会话 ID，重置 call_index 为 0 |
| `chat_id` | `set_chat_id()` | 当前对话轮次 ID |
| `call_index` | `_next_call_index()` / `reset_call_index()` | session 内 LLM 调用序号（从 1 自增） |
| `agent_name` | `set_current_agent()`（BIBaseAgent.on_messages_stream） | 当前执行的 Agent 名 |
| `enable_thinking` | `set_enable_thinking()`（DispatchLayer.run_stream） | 请求级思考模式覆盖（None=配置默认，True/False=强制） |
| `trace_recorder`（trace.py） | `set_trace_recorder()` | 当前任务的 TraceRecorder 实例 |

### 8.4 三路并行写入

| 写入路径 | 目标 | 触发点 |
|---|---|---|
| JSONL 文件 | `log/llm/*.jsonl` | LoggingChatCompletionClient 每次调用 |
| DB `llm_call` 表 | PostgreSQL | db_writer 异步批写入 |
| trace JSONL 文件 | `log/trace/*.jsonl` | TraceRecorder 每步 |

> DB 写入失败被 `try/except` 捕获并降级为 `logger.debug`，不影响主流程。

## 9. 优雅关闭

`BITeam.shutdown()`（`core/team.py`）执行以下清理，按顺序串行：

```
1. 标记 _shutdown=True，拒绝新请求
2. 清理 ContextVar（observability.logging_client + observability.trace）：
   - set_trace_recorder(None)
   - set_session_id("")
   - set_chat_id("")
   - set_current_agent("")
   - set_enable_thinking(False)
3. 停止 DB writer（db_writer.stop()）— 刷新队列中残余记录，5s 超时后强制取消
4. 关闭 PostgreSQL 连接池（db.close_pool()）
5. 关闭 SQL 连接池（tools.sql_query.close_sql_pool()）
```

每步都包裹 `try/except`，单步失败不影响后续清理，错误以 `WARNING` 记录。

**触发时机：**

- FastAPI 模式：`main.py` 使用 `uvicorn.Server` + `signal.signal(SIGINT)` 确保 Windows Ctrl+C 触发 lifespan shutdown；`gateway/app.py:lifespan` 的 shutdown 段，服务收到 SIGTERM/SIGINT 时
- 单进程 CLI 模式：进程退出时（Python 不保证 `atexit` 一定执行 async 清理，建议通过 Ctrl+C 触发 KeyboardInterrupt 让上层 `asyncio.run` 正常收尾）

**FastAPI 关闭顺序（`gateway/app.py:lifespan`）：**

```
1. db_writer.stop()
2. _team.shutdown() (若已初始化)
3. db.close_pool()
```

## 10. 健康检查

FastAPI 服务暴露 `GET /api/v1/health`，探测 DB 与 ES 依赖可达性。

### 10.1 检查项

| 检查 | 实现 | 判定 |
|---|---|---|
| DB 可达性 | 从 `db.get_pool()` 获取连接 → `SELECT 1` | 成功 `ok`，失败 `error: <msg 前100字>` |
| ES 可达性 | `utils.es_query.get_es_client()` → `client.ping()` | 成功 `ok`，失败 `error: ping failed` 或异常信息 |
| ES 索引状态 | `ensure_index_exists()` 检查资源索引是否存在 | 索引存在 `ok`，不存在则自动创建 |

### 10.2 响应示例

**全部正常：**

```json
{
  "status": "ok",
  "version": "0.1.0",
  "checks": {
    "db": "ok",
    "es": "ok",
    "es_index": "ok"
  }
}
```

**部分降级：**

```json
{
  "status": "degraded",
  "version": "0.1.0",
  "checks": {
    "db": "ok",
    "es": "error: connection refused",
    "es_index": "error: index not found"
  }
}
```

- `status`：所有检查均 `ok` 时为 `ok`，否则为 `degraded`
- 即便依赖异常，端点仍返回 200（便于负载均衡器基于 JSON 字段判断），不会抛 5xx
- 适合用于 K8s liveness/readiness probe（建议 readiness 才检查 status，liveness 仅检查端点可达）

### 10.3 部署后核对

部署完成后按顺序验证：

```bash
# 1. 依赖可达
curl http://localhost:8000/api/v1/health

# 2. 发起一次最小查询（CLI 单任务模式）
uv run python main.py 你好

# 3. 检查日志生成
```

## 附录：常见问题

**Q1: `uv sync` 报 `playwright` 安装失败？**
A: Playwright 内核需单独安装：`uv run playwright install chromium`。Linux 还需 `uv run playwright install-deps`。

**Q2: ES 连接报 `elasticsearch 8.x incompatible`？**
A: 必须使用 ES 7.10.2，依赖锁定 `elasticsearch7>=7.10.0,<8.0.0`。8.x 协议不兼容。

**Q3: `BI__DB_DSN` 为什么有两个下划线？**
A: pydantic-settings 字段名是 `_db_dsn`，env_prefix 是 `BI_`，下划线字段名拼接后形成 `BI_` + `_db_dsn` = `BI__DB_DSN`（双下划线）。优先级高于分字段配置。

**Q4: LLM 思考内容不展示？**
A: 检查 `BI_ENABLE_THINKING=True` + `BI_ENABLE_THINKING_OUTPUT=True`。前者控制发给模型的 `enable_thinking` 参数，后者控制是否向客户端推送 `THINK_CHUNK` 事件。Qwen3 通过 vLLM 部署时 `reasoning` 字段需经 `_patch_qwen3_reasoning()` 映射到 `reasoning_content`，模块加载时自动执行。

**Q5: 部署到生产后 CORS 报错？**
A: `BI_CORS_ORIGINS` 默认空数组=**不允许跨域**。生产必须显式配置：`BI_CORS_ORIGINS=["https://your-domain.com"]`。

**Q6: 单进程 CLI 模式下 DB 写入丢失？**
A: CLI 模式进程退出时未显式调用 `shutdown`。建议通过 `Ctrl+C` 让 `asyncio.run` 正常收尾，或在脚本中显式 `await team.shutdown()`。生产环境推荐用 FastAPI `--serve` 模式，lifespan 会保证 shutdown。

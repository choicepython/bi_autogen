
# 用户记忆模块方案设计

## 整体架构

```
┌─────────────────────────────────────────────────────┐
│                    用户记忆模块                       │
├───────────────┬─────────────────┬───────────────────┤
│  用户记忆      │  槽位记忆         │  知识记忆          │
│  你是谁        │  你做到哪了       │  你积累了什么       │
│  你喜欢什么    │  还差什么没做完    │  系统该知道什么      │
├───────────────┼─────────────────┼───────────────────┤
│  身份+偏好+同义词 │  任务进度追踪     │  LLM Wiki          │
│  静态为主      │  单 session 内有效  │  蒸馏、有版本       │
│  UserMemoryAgent管理 │  自动捕获   │  每日定时蒸馏       │
└───────────────┴─────────────────┴───────────────────┘
```

三层记忆与多轮对话上下文的关系：

| 维度 | 多轮对话上下文 | 用户记忆 | 槽位记忆 | 知识记忆 |
|------|--------------|---------|---------|---------|
| 生命周期 | 单 session 内 | 跨 session | 单 session 内 | 跨 session（持久） |
| 粒度 | 轮次级 | 用户级 | 任务级 | 知识级 |
| 触发 | 每次请求自动加载 | UserMemoryAgent主动操作 | 每次对话检索加载 | 每日定时蒸馏 |
| 内容 | 用户说了什么、Agent做了什么 | 用户是谁、偏好什么 | 任务进度、缺失信息 | 领域知识、术语、结论 |

## 用户记忆的提取与写入：UserMemoryAgent

### 核心设计原则

用户记忆的提取和写入**不是由规则引擎或指令剥离完成，而是由 UserMemoryAgent 通过工具调用完成**。

理由：

| 方案 | 问题 |
|------|------|
| 规则引擎/正则匹配 | 只能覆盖有限模式，"我是生产部的"这类输入无法被正则可靠识别 |
| 指令剥离（DispatchLayer预处理） | 需要额外LLM调用，且与路由层职责重叠 |
| 路由层LLM挂载记忆工具 | 路由层应保持纯决策，调用工具是执行行为，破坏无状态原则 |
| **UserMemoryAgent** | **复用已有的Agent+工具机制，路由层只负责识别意图并路由，Agent层执行记忆CRUD** |

关键洞察：**"用户要改记忆"和"用户要查数据"是同一层级的意图分类，路由层决定去哪个Agent，Agent层执行具体操作。** 这和现有架构完全一致——不需要新的预处理步骤，不需要破坏路由层的无状态性。

### UserMemoryAgent 定义

```python
class UserMemoryAgent(BIBaseAgent):
    """用户记忆管理 Agent：处理记忆增删改查。"""

    context_spec = ContextSpec(
        query_history="last",        # 只需要当前输入
        data_catalog="none",         # 不关心数据
        conclusions="none",
        user_knowledge="full",       # 需要知道已有记忆，避免重复
    )

    tools = [
        remember_preference,    # 记住偏好
        update_identity,        # 更新身份
        add_synonym,            # 添加术语映射
        remove_memory,          # 删除记忆
        query_memory,           # 查询已有记忆
    ]
```

### 记忆工具定义

```python
# tools/memory_tools.py

async def remember_preference(
    category: str,    # "agent" / "format" / "output" / "language"
    value: str,       # "SQLAgent" / "table" / "ppt" / "zh"
    reason: str = "", # LLM 填写的理由
) -> str:
    """记住用户的偏好设置。当用户表达"以后用XX"、"喜欢XX"、"不要XX"时调用。"""


async def update_identity(
    field: str,       # "department" / "role" / "data_scope"
    value: str,       # "生产部" / "工程师"
) -> str:
    """更新用户身份信息。当用户说"我是XX部门"、"我的角色是XX"时调用。"""


async def add_synonym(
    term: str,        # 用户使用的术语
    mapping: str,     # 系统中的标准字段/表名
    scope: str = "",  # 适用范围，如 "SQL查询" / "API参数"
) -> str:
    """添加术语映射。当用户纠正术语或说明"XX就是YY"时调用。"""


async def remove_memory(
    target: str,      # 要删除的记忆内容描述
) -> str:
    """删除用户记忆。当用户说"忘掉XX"、"删除XX偏好"时调用。"""


async def query_memory(
    query: str,       # 查询内容
) -> str:
    """查询当前用户的记忆内容。当用户问"你记住了什么"、"我的偏好是什么"时调用。"""
```

### 路由层的变化

路由层不需要挂载记忆工具，只需要在 Layer 3 的意图分类 prompt 中加入 UserMemoryAgent 作为可选目标：

```
现有 prompt:
  "根据用户意图分类到以下Agent: RAGAgent, APIAgent, SQLAgent, ..."

增强后:
  "根据用户意图分类到以下Agent: RAGAgent, APIAgent, SQLAgent, ..., UserMemoryAgent

   UserMemoryAgent: 用户表达偏好、纠正术语、声明身份、
   要求记住/忘记某些信息、查询已有记忆时路由到此Agent。
   例如: '我是生产部的'、'以后用SQL查'、'良率就是yield_rate'"
```

路由层仍然是纯决策——只是多了一个可选的 Agent 目标。

新增 AgentType：

```python
class AgentType(str, Enum):
    SEARCH = "RAGAgent"
    API = "APIAgent"
    SQL = "SQLAgent"
    PYFUNC = "PyFuncAgent"
    DATA_ANALYSIS = "DataAnalysisAgent"
    VISUALIZATION = "VisualizationAgent"
    REPORT = "ReportAgent"
    MEMORY = "UserMemoryAgent"      # 新增
```

### 三种场景的完整流程

#### 场景1：纯记忆操作

```
用户: "我是生产部的"

RoutingLayer:
  Layer 3 LLM → 意图=身份声明 → agent_type=MEMORY
  → RoutingResult(mode=SINGLE_AGENT, agent_type=MEMORY)

AgentLayer:
  UserMemoryAgent 执行 → 调用 update_identity(field="department", value="生产部")
  → 返回: "✓ 已记住：部门=生产部"

DispatchLayer:
  → yield MEMORY_UPDATED
  → yield SESSION_END
```

#### 场景2：记忆 + 查询混合

用户说"不对，良率是yield_rate，再查一下"，既包含纠正又包含查询。

路由层只能选一个 Agent，混合意图通过 **RoutingResult.pending_query + DispatchLayer 二次编排** 解决：

```python
class RoutingResult(BaseModel):
    # ... 现有字段 ...
    pending_query: str = ""  # 新增：记忆操作后的剩余查询
```

流程：

```
用户: "不对，良率是yield_rate，再查一下本月良率"

RoutingLayer:
  Layer 3 LLM → 意图=纠正+查询
  → RoutingResult(
      mode=SINGLE_AGENT,
      agent_type=MEMORY,           # 先处理记忆
      pending_query="再查一下本月良率",  # 附带剩余查询
    )

DispatchLayer:
  1. 先执行 UserMemoryAgent → add_synonym(term="良率", mapping="yield_rate")
     → 记忆立即生效（同义词写入）
  2. 检测到 pending_query 非空
  3. 用 pending_query 重新路由 → SQLAgent
  4. 执行 SQLAgent（此时 system prompt 已包含最新同义词: "良率=yield_rate"）
  5. SQL: SELECT yield_rate FROM ... ✓
```

DispatchLayer 的编排逻辑：

```python
# 执行完 UserMemoryAgent 后
if routing.agent_type == AgentType.MEMORY and routing.pending_query:
    # 混合意图：记忆操作后还有剩余查询，重新路由
    second_routing = await self._routing.route(routing.pending_query, ...)
    async for ev in self._agent_layer.run_single_agent(second_routing, ...):
        yield ev
```

**为什么不用 PlanAgent 编排混合意图？** PlanAgent 是 DAG 规划，对于"先改记忆再查"这种简单的两步串行，依赖 PlanAgent 反而增加了不确定性。DispatchLayer 的二次编排是确定性的，更可靠。

#### 场景3：纯查询

```
用户: "查一下本月产量"

RoutingLayer:
  Layer 3 LLM → 意图=数据查询 → agent_type=API
  → RoutingResult(mode=SINGLE_AGENT, agent_type=API)

→ 和现在完全一样，不涉及 UserMemoryAgent
```

### 事后纠正

用户看到结果后纠正——这是新一轮请求，自然走 UserMemoryAgent：

```
Turn 1: "查一下良率"
  → 路由到 SQLAgent → SELECT pass_rate → 结果

Turn 2: "不对，良率是yield_rate"
  → 路由到 UserMemoryAgent → add_synonym(term="良率", mapping="yield_rate")
  → pending_query 为空 → 纯记忆操作 → 结束
  → 可选: DispatchLayer 检测到纠正 + 上一轮有同主题查询
     → 自动追问: "是否用修正后的术语重新查询？"
```

### 记忆的撤销

```
用户: "忘掉我之前说的都用SQL查"
  → UserMemoryAgent → remove_memory(target="SQLAgent偏好")
  → ✓ 已移除偏好

用户: "你记住了什么？"
  → UserMemoryAgent → query_memory(query="所有")
  → 返回当前记忆摘要给用户
```

### 前端反馈

用户操作记忆后，系统必须确认，否则用户不知道改没改成功：

```
用户: "以后都用SQL查数据"
系统: ✓ 已记住：偏好使用 SQLAgent 查询数据

用户: "不对，良率是yield_rate"
系统: ✓ 已更新同义词：良率 → yield_rate
```

新增事件类型：

```python
class StreamEventType(str, Enum):
    ...
    MEMORY_UPDATED = "memory_updated"  # 新增：记忆已更新
```

### 隐式推断（补充 UserMemoryAgent 的不足）

UserMemoryAgent 处理的是**显式**记忆操作——用户主动说的。但有些偏好用户不会主动说，需要从行为中推断。

隐式推断**只做规则统计**，不做 LLM 推断。行为级偏好的深度推断交给每日 Wiki 蒸馏，避免两套 LLM 做类似的事。

| 来源 | 触发时机 | 处理方式 |
|------|---------|---------|
| Agent 使用分布 | 每次 session 结束后 | 规则引擎统计 preferred_agents 计数 |
| 输出格式选择 | 每次 session 结束后 | 规则引擎统计 preferred_format |
| 查询领域分布 | 每次 session 结束后 | 关键词/ES分类 → domain_interest |

隐式推断由 DispatchLayer 在 session 结束后执行，不经过 UserMemoryAgent。

**置信度机制：**

```
单次使用: confidence = 0.3
连续3次同类选择: confidence = 0.7
显式声明(UserMemoryAgent): confidence = 1.0

只有 confidence > 0.6 的偏好才注入到上下文中
低于阈值的只存储，不影响行为
```

## 第一层：用户记忆

### 包含什么

| 维度 | 内容 | 示例 | 写入方式 |
|------|------|------|---------|
| 身份 | 部门、角色、数据权限范围 | 生产部、工程师、可查MES数据 | UserMemoryAgent.update_identity |
| 偏好 | 常用Agent、输出格式、查询习惯 | 偏好SQLAgent、喜欢表格 | UserMemoryAgent.remember_preference + 隐式推断 |
| 同义词 | 用户自定义术语映射 | "良率"→"yield_rate" | UserMemoryAgent.add_synonym |

### 如何保存

```
写入时机:
  - 显式操作: UserMemoryAgent 工具调用时（立即写入）
  - 隐式推断: session 结束后（仅规则引擎统计，不做 LLM 推断）

写入方式: 增量更新，不覆盖
  - preferred_agents: 计数累加
  - synonym_map: 追加新映射（不删除旧的）
  - domain_interest: 滑动窗口，保留最近30天

衰减机制:
  - 30天未使用的偏好 confidence 衰减50%
  - 60天未使用的偏好移除
  - 显式声明和同义词不衰减

同义词的唯一存储位置:
  - 同义词映射只存在 profile 层，不进入 Wiki
  - 理由: 同义词是确定性映射，不适合 LLM 蒸馏（可能出错）
  - Wiki 蒸馏时跳过术语映射，只提炼行为级知识
```

## 第二层：槽位记忆

### 什么是槽位

槽位 = **当前 session 内的任务进度追踪**。不是对话历史，是任务进度条。

**核心约束：槽位只在单 session 内有效，新 session 不加载旧槽位。**

用户创建新 session 的目的是隔离任务，槽位不应跨 session 续接。如果用户想继续之前的任务，应该在新 session 中重新描述需求。

槽位持久化到 DB 的目的是**同 session 多轮之间保持状态**：每次 HTTP 请求时从 DB 加载当前 session 的槽位，确保多轮对话中槽位状态不丢失。

### BI 场景下的典型槽位

```
场景1: 多步任务进度追踪
  用户: "帮我分析一下产量数据"
  系统: PlanAgent 规划 [APIAgent查数据 → DataAnalysisAgent分析]
  → 槽位: {task: "产量分析", status: "in_progress", completed: [], pending: [查数据, 分析]}

  APIAgent 执行完成 →
  → 槽位: {status: "in_progress", completed: [查数据], pending: [分析]}

  DataAnalysisAgent 执行完成 →
  → 槽位: {status: "completed"}

场景2: Agent 请求参数补充
  用户: "帮我查一下产量"
  → APIAgent → ask_user("哪个时间范围？", "时间范围")
  → 槽位: {status: "waiting_input", missing: ["时间范围"]}

  用户回答: "本月的"
  → 槽位: {status: "in_progress", missing: []}
  → APIAgent 带着完整参数继续执行

场景3: 任务中断（session 内多轮）
  用户: "帮我分析产量数据"
  → PlanAgent 规划 [查数据, 分析, 生成报告]
  → 执行到第2步时，用户: "先停一下"
  → 槽位: {status: "partial", completed: [查数据], pending: [分析, 生成报告]}

  用户: "继续"
  → 从 pending_steps 继续执行
```

### 槽位的数据模型

```python
class SlotStatus(str, Enum):
    WAITING_INPUT = "waiting_input"   # 等待用户补充信息（ask_user 触发）
    IN_PROGRESS = "in_progress"       # 执行中
    PARTIAL = "partial"               # 部分完成，用户暂停
    COMPLETED = "completed"           # 已完成

class Slot(BaseModel):
    """单 session 内的任务进度追踪，新 session 不加载。"""
    slot_id: str                       # 槽位唯一ID
    session_id: str                    # 所属 session（隔离边界）
    user_id: str                       # 所属用户
    intent: str                        # 用户意图描述
    status: SlotStatus                 # 当前状态

    # 已完成的部分
    completed_steps: list[StepRecord]  # [{agent, result_summary, data_ref}]

    # 待完成的部分
    pending_steps: list[PendingStep]   # [{task_id, description, agent_name}]

    # 缺失信息（ask_user 触发）
    missing_params: list[MissingParam] # [{param: "时间范围", prompt: "...", value: ""}]

    # 时间戳
    created_at: str
    updated_at: str

class StepRecord(BaseModel):
    agent: str
    result_summary: str
    data_refs: list[str]               # DataContext keys

class PendingStep(BaseModel):
    task_id: str                       # 任务ID（对应 DAGPlan 中的 task_id）
    description: str                   # 任务描述
    agent_name: str                    # 负责的 Agent 名称

class MissingParam(BaseModel):
    param: str                         # 缺失参数名
    prompt: str                        # 向用户提问的话术
    options: list[str] = []            # 可选项
    value: str = ""                    # 用户补充的值（填充后设置）
```

### 如何捕获槽位

**核心问题：怎么知道一个任务"没做完"？**

两种触发方式，**不使用 LLM 意图闭环检测**：

---

#### 触发方式1：结构检测（规则引擎，零 LLM 成本）

通过系统内部结构化信息判断任务未完成，无需 LLM 推理：

| 检测规则 | 触发条件 | 槽位状态 |
|---------|---------|-----------|
| DAG 未完成 | PlanAgent 规划了 N 个任务，当前只完成 M 个（M < N） | `PARTIAL`, `pending_steps=剩余任务` |
| Agent 执行失败 | Agent 抛出异常或返回 ERROR 事件 | `PARTIAL`, `pending_steps=[失败的任务]` |
| Agent 被跳过 | DAG 中某 Agent 因前置条件不满足被跳过 | `PARTIAL`, `pending_steps=[被跳过的任务]` |
| 显式中断 | 用户说"等一下"、"先不做了"、"暂停" | `PARTIAL` |

**实现位置**：DispatchLayer 实时维护，纯规则逻辑，不调用 LLM。

```python
# DispatchLayer 实时维护槽位
def _update_slot_from_plan(self, context: SessionContext) -> Slot | None:
    """根据 DAG 执行状态更新槽位。"""
    plan = context.current_plan
    if plan is None:
        return None

    completed = [t for t in plan.tasks if t.status == "completed"]
    pending = [t for t in plan.tasks if t.status not in ("completed", "skipped")]
    skipped = [t for t in plan.tasks if t.status == "skipped"]

    if not pending and not skipped:
        return None

    return Slot(
        intent=context.original_query,
        status=SlotStatus.PARTIAL,
        completed_steps=self._build_step_records(completed),
        pending_steps=[
            PendingStep(task_id=t.id, description=t.description, agent_name=t.agent_name)
            for t in (pending + skipped)
        ],
        missing_params=[],
    )
```

#### 触发方式2：ask_user 工具（Agent 主动请求补充信息）

当 Agent 执行过程中发现缺少必要参数（如时间范围、数据源、筛选条件），通过 `ask_user` 工具主动向用户提问。

**核心设计：ask_user 在当前 session 内暂停 Agent 执行，等待用户回答后继续。**

```python
# tools/ask_user.py

async def ask_user(
    question: str,           # 向用户提问的内容
    param_name: str,         # 缺失参数名
    options: list[str] = [], # 可选项
) -> str:
    """当执行任务需要用户提供额外信息时调用。
    调用后任务暂停，等待用户在当前 session 内回答。

    示例:
      - ask_user("您需要哪个时间范围的产量数据？", "时间范围", ["本月", "上月", "本季度"])
      - ask_user("请指定要分析的产线", "产线", ["A线", "B线", "C线"])
    """
    # 返回特殊标记，由 EventTranslator 捕获并生成 CLARIFICATION 事件
    return f"__CLARIFICATION_NEEDED__:{param_name}:{question}"
```

**ask_user 的执行流程：**

```
Agent 执行中 → 发现缺少"时间范围"参数
  → 调用 ask_user("您需要哪个时间范围？", "时间范围", ["本月", "上月"])
  → ask_user 返回 "__CLARIFICATION_NEEDED__:时间范围:您需要哪个时间范围？"
  → EventTranslator 捕获标记 → yield CLARIFICATION 事件
  → DispatchLayer 检测到 CLARIFICATION 事件
     → 更新当前 Slot: status=WAITING_INPUT, missing_params=[{param="时间范围", ...}]
     → yield CLARIFICATION 事件给前端
     → 暂停当前 Agent 执行，等待用户回答

用户在同一 session 回答: "本月的"
  → DispatchLayer 检测到当前 session 有 WAITING_INPUT 状态
     → 用用户回答填充 missing_params
     → 将填充值注入 ChatRequest.prefilled_params
     → Slot: status=IN_PROGRESS, missing_params=[]
     → 继续执行当前 Agent（带着完整参数）
```

**新增事件类型：**

```python
class StreamEventType(str, Enum):
    ...
    CLARIFICATION = "clarification"  # 新增：Agent 请求用户补充信息
```

```python
# CLARIFICATION 事件结构
StreamEvent(
    type=StreamEventType.CLARIFICATION,
    agent_name="APIAgent",
    content="您需要哪个时间范围的产量数据？",
    data={
        "param_name": "时间范围",
        "options": ["本月", "上月", "本季度"],
    },
)
```

**参数填充值如何传递给 Agent：**

Agent 不会自动知道缺失参数已被填充。需要通过 `ChatRequest` 传递：

```python
class ChatRequest(BaseModel):
    ...
    prefilled_params: dict[str, str] = {}  # ask_user 回答后填充的参数
```

DispatchLayer 在用户回答后注入：

```python
# 用户回答后继续执行
req = ChatRequest(
    query=original_query,
    prefilled_params={"时间范围": "本月"},
)
```

Agent prompt 中追加注入：

```
用户已明确指定以下参数：
- 时间范围: 本月
请使用这些参数执行，不要再询问。
```

**如果用户未回答就离开：** session 结束，槽位归档。用户下次新 session 需要重新发起请求。

---

#### 为什么不使用 LLM 意图闭环检测

| 考量 | 分析 |
|------|------|
| 成本 | 每次 session 结束额外调用一次 LLM，增加延迟和 token 消耗 |
| 可靠性 | "意图是否满足"是主观判断，LLM 误判率高（尤其中文 BI 场景） |
| 覆盖度 | 结构检测已覆盖 DAG 未完成、Agent 失败/跳过等主要场景；ask_user 覆盖参数缺失场景 |
| 可调试性 | 规则引擎的结果可追溯、可调试；LLM 判断是黑盒 |

如果未来需要更精细的意图闭环检测，可以作为**第三种触发方式**独立加入，但不作为 MVP 方案。

### 槽位的生命周期

```
创建（两种触发）:
  ├─ 结构检测 → PARTIAL（DAG未完成/Agent失败/Agent跳过/显式中断）
  └─ ask_user  → WAITING_INPUT（Agent请求参数补充）
  ↓
执行: DispatchLayer 实时维护，每次变更写 DB
  - 每完成一个 Agent → 追加到 completed_steps，从 pending_steps 移除
  - ask_user 触发 → status=WAITING_INPUT，等待用户回答
  - 用户回答 → 填充 missing_params → status=IN_PROGRESS
  ↓
完成: 所有 pending_steps 执行完毕 且 missing_params 为空 → COMPLETED
  ↓
销毁: session 结束时，该 session 的所有槽位标记为已完成，不再被新 session 加载
```

**槽位的实时更新逻辑：**

```python
def _update_slot_on_event(self, slot: Slot, event: StreamEvent) -> None:
    """根据事件实时更新槽位。"""
    # Agent 完成 → 追加到 completed_steps
    if event.type == StreamEventType.AGENT_END and event.data.get("status") == "success":
        slot.completed_steps.append(StepRecord(
            agent=event.agent_name,
            result_summary=event.content,
            data_refs=event.data.get("data_refs", []),
        ))
        slot.pending_steps = [
            p for p in slot.pending_steps if p.agent_name != event.agent_name
        ]

    # ask_user 触发 → 追加 missing_params
    elif event.type == StreamEventType.CLARIFICATION:
        slot.missing_params.append(MissingParam(
            param=event.data["param_name"],
            prompt=event.content,
            options=event.data.get("options", []),
        ))
        slot.status = SlotStatus.WAITING_INPUT

    # 判断完成
    if not slot.pending_steps and not slot.missing_params:
        slot.status = SlotStatus.COMPLETED
    elif slot.status != SlotStatus.WAITING_INPUT:
        slot.status = SlotStatus.IN_PROGRESS
```

### 槽位的检索与加载

每次对话请求时，DispatchLayer 从 DB 加载**当前 session** 的槽位：

```python
async def _load_session_slot(self, session_id: str) -> Slot | None:
    """加载当前 session 的活跃槽位。"""
    return await slot_store.query_one(
        session_id=session_id,
        status_not_in=[SlotStatus.COMPLETED],
    )
```

**关键：按 session_id 检索，不是按 user_id。** 新 session 不会加载旧 session 的槽位。

### 槽位的 session 内交互

**同 session 多轮 — ask_user 在 session 内解决：**

```
用户: "帮我查一下产量"
  → APIAgent → ask_user("哪个时间范围？", "时间范围")
  → Slot: {status=WAITING_INPUT, missing=[时间范围]}

用户(同session): "本月的"
  → 填充 missing_params → Slot: {status=IN_PROGRESS}
  → 构建 ChatRequest(prefilled_params={"时间范围": "本月"})
  → 继续执行 APIAgent
```

**如果用户未回答就离开：** session 结束，槽位随 session 结束。用户下次新 session 需要重新发起请求。

**PARTIAL 状态 — 用户暂停后继续：**

```
用户: "帮我分析产量数据"
  → PlanAgent 规划 [查数据, 分析, 生成报告]
  → 执行到第2步时，用户: "先停一下"
  → Slot: {status=PARTIAL, completed=[查数据], pending=[分析, 生成报告]}

用户(同session): "继续"
  → DispatchLayer 检测到当前 session 有 PARTIAL 槽位
  → 从 pending_steps 继续执行
```

**WAITING_INPUT 的参数匹配逻辑：**

```python
def _try_fill_missing_params(self, slot: Slot, user_input: str) -> bool:
    """尝试用用户输入填充缺失参数。"""
    if slot.status != SlotStatus.WAITING_INPUT:
        return False

    filled = []
    for mp in slot.missing_params:
        if mp.options:
            for opt in mp.options:
                if opt in user_input:
                    mp.value = opt
                    filled.append(mp)
                    break
        else:
            mp.value = user_input
            filled.append(mp)

    if filled:
        slot.missing_params = [mp for mp in slot.missing_params if mp not in filled]
        if not slot.missing_params:
            slot.status = SlotStatus.IN_PROGRESS
        return True
    return False
```

### 为什么槽位不跨 session

| 考量 | 分析 |
|------|------|
| 任务隔离 | 用户创建新 session 的目的就是隔离任务，跨 session 加载旧槽位违背此意图 |
| 上下文一致性 | 旧槽位的 DataContext（DataFrame）在新 session 中不存在，续接后数据引用失效 |
| 简单性 | 不需要语义匹配、槽位冲突处理、过期清理等复杂机制 |
| 用户预期 | 用户在新 session 中期望全新的开始，而非被旧任务打断 |

三层记忆的职责分工：
- **用户记忆**（跨 session）：记住"你是谁、你喜欢什么" — 静态身份
- **知识记忆**（跨 session）：记住"你积累了什么" — 沉淀认知
- **槽位记忆**（单 session）：追踪"你做到哪了" — 当前任务进度，session 结束即归零

---

## 第三层：知识记忆

### 核心理念

知识记忆不是对话历史的堆砌，是**蒸馏后的 LLM Wiki** — 一份系统级文档，告诉 LLM "关于这个用户，你需要知道什么"。

### 为什么是 Wiki 而不是知识条目列表

| 方案 | 优点 | 缺点 |
|------|------|------|
| 条目列表 | 简单、可检索 | 碎片化、缺乏关联、检索噪声大 |
| LLM Wiki | 结构化、有上下文、LLM 友好 | 需要定期蒸馏、更新成本高 |

选 Wiki 的原因：**LLM 读一段结构化的文档，比读 50 条碎片知识条目效果好得多**。Wiki 把零散知识组织成了 LLM 能直接理解的形式。

### Wiki 的内容结构

> **注意**：术语映射不存入 Wiki，由用户记忆（profile 层）统一管理。
> 原因：同义词是确定性映射，不适合 LLM 蒸馏（可能出错），应由用户显式声明。
> Wiki 只提炼需要推断的行为级知识。

```markdown
# 用户知识 Wiki: 张三

## 业务背景
- 生产部工程师，负责 MES 系统数据分析
- 主要关注: 产量、良率、设备OEE
- 数据权限: MES生产库、质量检测库

## 数据源认知
- 常用API: production_output(产量查询)、yield_rate(良率查询)、equipment_oee(设备效率)
- 常用SQL表: mes.production_daily, quality.yield_summary
- 数据粒度偏好: 月度汇总 > 日明细

## 分析习惯
- 对比分析时习惯用同比（非环比）
- 预测偏好 ARIMA 模型
- 异常检测用 Z-Score 方法
- 报告格式偏好 PPT，模板用深色主题

## 历史结论
- 2026-Q1 产量同比+12%，良率持平
- 2026-03 设备OEE异常下降，原因是产线A停机检修
- 2026-06 产量预测约 5200 件/月

## 已知约束
- MES数据T+1更新，当天查不到实时数据
- quality库查询需要额外权限审批
- 产量数据单位为"件"，非"台"
```

### 如何提炼 Wiki

采用**定时任务 + 对话历史蒸馏**模式，每天对活跃用户的对话历史进行一次 LLM 蒸馏，增量更新 Wiki。

#### 数据流

```
用户对话 → session 写入 DB（已有机制）
                ↓
每日定时任务（凌晨低峰期）
  → 扫描昨日有新 session 的用户
  → 读取用户对话历史（session 摘要 + Agent 结论）
  → 读取当前 Wiki
  → LLM 增量蒸馏 → 新版 Wiki
  → 写入 DB + 版本号递增
```

#### 定时任务设计

```python
# core/wiki_distiller.py

class WikiDistiller:
    """每日定时蒸馏任务：对话历史 → 用户 Wiki。"""

    async def run_daily(self) -> dict[str, int]:
        """执行每日蒸馏，返回 {user_id: new_version}。"""
        # 1. 找出昨日有新 session 的活跃用户
        active_users = await self._get_active_users(since="yesterday")
        results = {}
        for user_id in active_users:
            try:
                version = await self._distill_user(user_id)
                if version:
                    results[user_id] = version
            except Exception as e:
                logger.warning(f"Wiki蒸馏失败 user={user_id}: {e}")
        return results

    async def _distill_user(self, user_id: str) -> int | None:
        """为单个用户蒸馏 Wiki。"""
        # 1. 读取当前 Wiki
        current_wiki = await self._load_wiki(user_id)

        # 2. 读取自上次蒸馏以来的对话历史
        sessions = await self._load_recent_sessions(
            user_id,
            since_version=current_wiki.version if current_wiki else 0,
        )
        if not sessions:
            return None  # 无新对话，跳过

        # 3. 构建蒸馏 prompt
        prompt = self._build_distill_prompt(current_wiki.text, sessions)

        # 4. LLM 增量蒸馏
        new_wiki_text = await self._call_llm(prompt)

        # 5. 写入新版本
        new_version = (current_wiki.version if current_wiki else 0) + 1
        await self._save_wiki(user_id, new_wiki_text, new_version)
        return new_version
```

#### 对话历史读取

蒸馏的输入是**用户对话历史**，不是知识条目列表。对话历史来自已有的 DB session 表：

```python
async def _load_recent_sessions(self, user_id: str, since_version: int) -> list[SessionSummary]:
    """读取自上次蒸馏以来的对话历史摘要。"""
    # 从 session + routing + agent_execution 表聚合
    # 每个session生成一份摘要：
    #   - 用户query
    #   - 路由到的Agent
    #   - Agent执行结论（final_result）
    #   - 用户纠正（如有）
    #   - 使用的工具和数据源
    ...
```

**为什么用对话历史而非知识条目？**

| 输入 | 优点 | 缺点 |
|------|------|------|
| 知识条目列表 | 结构化、去重容易 | 需要额外的实时捕获逻辑，捕获遗漏则蒸馏遗漏 |
| **对话历史** | **已有数据（session表），无需额外捕获逻辑；LLM从原始对话中提炼更准确** | token消耗稍高 |

选对话历史的原因：**session 数据已经在 DB 中（现有机制），不需要额外的实时捕获步骤**。LLM 直接从对话中提炼，比从预提取的条目中提炼更完整——因为"什么值得记住"的判断交给蒸馏 LLM，而非捕获时的规则。

#### 蒸馏 Prompt

```
你是一个用户知识提炼助手。根据用户的对话历史，更新其知识 Wiki。

## 当前 Wiki
{current_wiki}

## 近期对话历史
{session_summaries}

## 更新规则
1. 保留仍然有效的旧知识
2. 从新对话中提炼以下类型的知识：
   - 数据源认知：用户常用的API/SQL表/数据源
   - 分析习惯：用户偏好的分析方法、输出格式
   - 业务约束：用户提到的数据规则、权限限制
   - 历史结论：重要的分析结论（仅保留最近3个月）
   注意：术语映射不在 Wiki 中提炼，由用户记忆（profile层）统一管理
3. 合并重复信息，移除过时信息
4. 总长度控制在 800 token 以内
5. 保持 Markdown 格式，使用已有的章节标题
6. 优先保留"纠正"和"约束"类知识（不可替代），压缩"结论"类（可重新查询）

输出更新后的完整 Wiki：
```

#### 定时任务调度

```
调度方式: 系统内置定时任务（APScheduler / asyncio 定时循环）
执行时间: 每天凌晨 02:00（低峰期）
并发控制: 逐用户串行执行，避免 LLM 限流
跳过条件: 用户昨日无新 session → 跳过
超时: 单用户蒸馏超时 30s → 跳过该用户
```

**为什么不用 session 计数触发？**

| 触发方式 | 问题 |
|---------|------|
| 累计5个session触发 | 高频用户可能一天触发多次，低频用户可能一周才5个session |
| **每日定时** | **简单、可预测、低峰执行、所有用户统一处理** |

### 蒸馏的关键设计

**1. 递增式蒸馏，不是全量重写**

```
✗ 每次都从所有历史session重新生成 → 成本高、信息丢失
✓ 输入旧Wiki + 近期对话历史 → LLM增量更新 → 输出新Wiki
```

**2. 长度控制**

Wiki 必须控制在 800 token 以内（约 1200 字），否则会挤占 Agent 的上下文窗口。

控制策略：
- 历史结论只保留最近 3 个月
- 数据源认知只保留近期使用的
- 分析习惯只保留明确确认的
- 如果超长，LLM 蒸馏时优先保留"约束"类知识（不可替代），压缩"结论"类（可重新查询）

**3. 版本管理**

```
wiki_v1: 2026-07-01 初版（首次蒸馏，基于用户所有历史session）
wiki_v2: 2026-07-02 更新（基于昨日对话增量蒸馏）
wiki_v3: 2026-07-03 更新（基于昨日对话增量蒸馏）

保留最近3个版本，支持回滚
```

**4. 首次蒸馏 vs 增量蒸馏**

```
首次蒸馏（用户无 Wiki 时）:
  输入: 用户最近30天的对话历史
  输出: 初始 Wiki

增量蒸馏（用户已有 Wiki 时）:
  输入: 旧Wiki + 昨日对话历史
  输出: 更新后的 Wiki
```

首次蒸馏窗口较大（30天），因为需要从零建立用户画像；后续增量蒸馏只看最近1天，控制 token 消耗。

### Wiki 如何注入系统

```
方式: 作为系统提示词的一部分注入

注入点:
  - BIBaseAgent 的 system prompt 末尾追加 Wiki 文本
  - Wiki 本身已控制在 800 token 以内，全量注入成本可控

  ContextSpec.user_knowledge:
    "none"     → 不注入
    "full"     → 注入完整 Wiki

  MVP 阶段不提供 "relevant" 按段落检索模式。
  理由：Wiki 是精炼摘要（800 token），不是长文档，全量注入即可。
  如果未来 Wiki 增长到需要分段，再引入段落切分+嵌入检索。

各 Agent 的声明:
  RAGAgent:           user_knowledge="full"      # 知识问答需要完整上下文
  SQLAgent:           user_knowledge="full"      # 需要数据源认知和业务约束
  PlanAgent:          user_knowledge="full"      # 规划需要完整用户画像
  APIAgent:           user_knowledge="full"      # 需要数据源认知和API习惯
  VisualizationAgent: user_knowledge="full"      # 需要分析习惯和格式偏好
  UserMemoryAgent:    user_knowledge="full"      # 需要知道已有记忆，避免重复
```

## 三层记忆的协作关系

```
用户(新session): "预测下个月的产量趋势"

DispatchLayer:
  1. 加载用户记忆 → {生产部, 偏好SQLAgent, 偏好ARIMA}
  2. 加载知识记忆 → Wiki片段: "常用API=production_output, 偏好ARIMA"
  3. 槽位记忆 → 新 session，无旧槽位

  4. 组装上下文:
     - 用户记忆 → 注入 RoutingContext（偏好SQLAgent → 路由加权）+ 同义词映射（良率=yield_rate）
     - 知识记忆 → 注入 Agent system prompt（数据源认知 + 分析习惯）

  5. 路由 → DataAnalysisAgent
     DataAnalysisAgent 收到:
       - 用户记忆: "良率=yield_rate"（从 profile 注入的同义词）
       - 知识: "偏好ARIMA模型"（从Wiki注入）

  6. 执行过程中:
     - DataAnalysisAgent 发现缺少时间范围 → ask_user → 创建 Slot(WAITING_INPUT) → 写DB
     - 用户回答 "下个月" → Slot(IN_PROGRESS) → 写DB → 继续执行
     - 执行完成 → Slot(COMPLETED) → 写DB
     - session 结束 → 槽位归档，新 session 不会加载
```

## 三层记忆的写入时机汇总

| 时机 | 用户记忆 | 槽位记忆 | 知识记忆 |
|------|---------|---------|---------|
| Session 开始 | 读取 | **按 session_id 加载当前槽位** | 读取 |
| 路由阶段 | 路由到UserMemoryAgent | — | — |
| UserMemoryAgent执行 | **工具调用写入记忆** | — | — |
| Agent 执行中 | — | **ask_user → WAITING_INPUT + 写DB** | — |
| Agent 执行中 | — | **实时更新步骤状态 + 写DB** | — |
| 用户回答补充信息 | — | **填充 missing_params → IN_PROGRESS + 写DB** | — |
| Session 结束 | 规则引擎统计偏好计数 | **槽位归档（不再被新 session 加载）** | — |
| 每日定时任务 | — | 清理历史归档槽位 | **定时蒸馏Wiki** |

## 存储选型

| 记忆层 | 推荐存储 | 理由 |
|--------|---------|------|
| 用户记忆 | PostgreSQL (JSONB) | 结构化、小数据量、需要事务 |
| 槽位记忆 | PostgreSQL (JSONB) | 同 session 多轮持久化，按 session_id 隔离 |
| 知识记忆-Wiki | PostgreSQL (TEXT + 版本号) | 纯文本、版本管理、定时任务写入 |

三层共用一张 `user_memory` 主表，按 `memory_type` 区分：

```sql
user_memory (
  user_id,
  session_id,     -- 槽位专用：session 隔离，新 session 不加载旧槽位
  memory_type,    -- "profile" / "slot" / "wiki"
  data JSONB,
  wiki_text TEXT,  -- Wiki 专用：存储完整 Wiki 文本
  version INT,
  updated_at TIMESTAMP
)
```

槽位检索条件：`WHERE session_id = ? AND memory_type = 'slot'`，确保新 session 不会加载旧 session 的槽位。

Wiki 蒸馏的对话历史直接从已有的 `session` + `routing` + `agent_execution` 表聚合读取，无需额外的知识条目表。

## Redis 持久化存储

三层记忆之外，系统还提供两个基于 Redis 的持久化存储能力，用于跨轮对话的状态恢复。两者均通过 `store_factory.py` 按 `BI_REDIS_URL` 配置选择 Redis 或 InMemory 实现，连接失败自动降级为 InMemory。

### RedisConversationStore（会话存储）

跨轮对话的会话历史持久化，解决 HTTP 无状态下单进程多实例间会话丢失问题。

| 项 | 说明 |
|---|---|
| 数据结构 | Redis LIST，每个 session 一个 key |
| TTL | 7200s（2 小时），到期自动过期 |
| Key 规则 | `bi:conv:{session_id}` |
| 写入 | 每轮对话结束后追加消息到 LIST 尾部 |
| 读取 | 新请求到来时按 `session_id` 从 LIST 读取全部历史消息 |

**降级策略**：`BI_REDIS_URL` 为空或连接失败时，`store_factory.create_conversation_store()` 返回 `InMemoryConversationStore`，会话历史仅在单进程内存中有效，进程重启后丢失。

### RedisDataContextCache（DataContext 缓存）

跨轮对话的 DataContext 持久化，让下游 Agent 能引用前序轮次产出的 DataFrame。

| 项 | 说明 |
|---|---|
| 数据结构 | Redis SET（key 索引）+ DataFrame JSON 序列化 |
| Key 规则 | 索引 `bi:dc:{session_id}`（SET）；数据 `bi:dc:{session_id}:{data_key}` |
| 序列化 | DataFrame → JSON（含 dtypes、index、columns） |
| 写入 | Agent 执行后 `put()` 将 DataFrame 序列化写入，并 `SADD` 到索引 SET |
| 读取 | 新请求到来时按 `session_id` 从索引 SET 取全部 key，反序列化恢复 DataContext |

**降级策略**：`BI_REDIS_URL` 为空或连接失败时，`store_factory.create_data_context_cache()` 返回 `InMemoryDataContextCache`，DataContext 不跨进程持久化，跨轮对话需重新获取数据。

**跨轮恢复流程**：

```
新请求到达（携带 session_id）
    ↓
store_factory 按 BI_REDIS_URL 选择实现
    ↓
RedisConversationStore.load(session_id) → 恢复会话历史消息
RedisDataContextCache.load(session_id)  → 恢复 DataContext（DataFrame）
    ↓
DispatchLayer 用恢复的 DataContext 创建 AgentLayer
    ↓
本轮 Agent 可直接引用前序轮次产出的数据（data_key 不变）
```

## 已解决的设计决策

| 问题 | 决策 | 理由 |
|------|------|------|
| add_knowledge 工具是否有必要 | **删除**，知识由每日蒸馏从对话历史提炼 | 无独立存储目标（knowledge_entry 表已移除），蒸馏从 session 历史提炼更完整 |
| 同义词映射存 Wiki 还是 profile | **只存 profile 层** | 同义词是确定性映射，不适合 LLM 蒸馏（可能出错），应由用户显式声明 |
| 隐式推断是否需要 LLM | **不需要**，只做规则统计 | 行为级偏好的深度推断交给每日 Wiki 蒸馏，避免两套 LLM 做类似的事 |
| ask_user 是否强制结束 session | **不强制**，同 session 内等待用户回答后继续 | 多轮对话中用户可能立即回答，无需新建 session |
| pending_steps 的类型 | **结构化 PendingStep**（含 task_id/description/agent_name） | 纯字符串无法与 completed_steps 的 agent 名匹配 |
| Wiki 注入是否需要 relevant 模式 | **MVP 不需要**，只保留 none/full | Wiki 是 800 token 精炼摘要，全量注入成本可控；relevant 需要段落切分+嵌入 |
| ask_user 回答后参数如何传递给 Agent | **ChatRequest.prefilled_params + prompt 注入** | Agent 不会自动知道缺失参数已填充，需要显式传递 |
| 槽位是否跨 session | **不跨 session**，按 session_id 隔离，新 session 不加载旧槽位 | 用户创建新 session 的目的是隔离任务；三层记忆各有分工——用户记忆/知识记忆跨 session，槽位记忆单 session |

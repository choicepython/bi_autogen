## 1. 数据库概览

### 1.1 数据库选型

| 项 | 说明 |
|---|---|
| 数据库 | PostgreSQL |
| 驱动 | `asyncpg`（纯异步、高性能，原生支持 PostgreSQL 类型） |
| 扩展 | `pgcrypto`（提供 `gen_random_uuid()` 用于主键生成） |
| DDL 文件 | `db/schema.sql` |
| 连接池 | `db/pool.py` |
| 写入器 | `db/writer.py` |
| 监控查询 | `db/metrics.py` |

### 1.2 设计原则

- **幂等建表**：所有 `CREATE TABLE` / `CREATE INDEX` 均使用 `IF NOT EXISTS`，重复执行 schema.sql 不会报错
- **中文注释全覆盖**：8 张表均带 `COMMENT ON TABLE`，所有字段均带 `COMMENT ON COLUMN`，便于运维和 DBA 直接查询元数据
- **外键级联删除**：7 张子表通过复合外键 `FOREIGN KEY (session_id, chat_id) REFERENCES session(session_id, chat_id) ON DELETE CASCADE` 关联到 `session` 主表，删除会话即可级联清理所有子记录
- **复合主键设计**：业务键为 `(session_id, chat_id)` 二元组 —— `session_id` 标识会话，`chat_id` 标识多轮对话中的具体轮次；所有子表沿用该二元组作为外键
- **审计字段统一**：每张表均有 `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` 和 `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
- **JSONB 扩展字段**：每张表都有 `extra JSONB DEFAULT '{}'`，便于后续迭代新字段时不破坏 schema

### 1.3 表清单

| # | 表名 | 中文名 | 用途 |
|---|------|--------|------|
| 1 | `session` | 会话主表 | 记录每次用户交互的完整生命周期 |
| 2 | `routing_decision` | 路由决策记录 | 记录 3 层路由的判断结果 |
| 3 | `dag_plan` | DAG 规划记录 | 记录 PlanAgent 输出的任务编排 |
| 4 | `agent_execution` | Agent 执行记录 | 记录每个智能体的运行状态和性能 |
| 5 | `tool_call` | 工具调用记录 | 记录 Agent 调用的每个工具入参与结果 |
| 6 | `llm_call` | LLM 调用记录 | 记录每次大模型请求和响应 |
| 7 | `session_feedback` | 用户反馈 | 收集用户对回答质量的评价 |
| 8 | `data_context_snapshot` | DataContext 数据快照 | 异步归档 Agent 间传递的 DataFrame |

### 1.4 启用扩展

```sql
CREATE EXTENSION IF NOT EXISTS "pgcrypto";
```

`pgcrypto` 提供 `gen_random_uuid()` 函数，被所有 8 张表的主键 `DEFAULT gen_random_uuid()` 引用。PostgreSQL 13+ 已内置 `gen_random_uuid()`，但显式 `CREATE EXTENSION` 保证在所有版本上可用。

## 2. 8 张表详解

### 2.1 `session` — 会话主表

**用途**：记录每次用户交互的完整生命周期，是所有子表的父表。

#### 字段定义

| 字段 | 类型 | 默认值 | 约束 | 中文注释 |
|------|------|--------|------|----------|
| `id` | UUID | `gen_random_uuid()` | PRIMARY KEY | 主键 UUID |
| `session_id` | VARCHAR(64) | — | NOT NULL, UNIQUE 组合 | 业务会话 ID，格式 YYYYMMDD_HHMMSS |
| `chat_id` | VARCHAR(64) | `''` | UNIQUE 组合 | 对话轮次 ID，多轮对话时使用 |
| `query` | TEXT | — | NOT NULL | 用户原始问题 |
| `status` | VARCHAR(20) | `'running'` | NOT NULL | 状态：running/completed/failed/cancelled/cached |
| `execution_mode` | VARCHAR(20) | `''` | — | 执行模式：single_agent/full_team |
| `result` | TEXT | `''` | — | 最终回答内容（截断到 10000 字符） |
| `error_message` | TEXT | `''` | — | 错误信息（失败时记录） |
| `user_id` | VARCHAR(64) | `''` | — | 用户 ID |
| `user_name` | VARCHAR(128) | `''` | — | 用户姓名 |
| `source_site` | VARCHAR(64) | `'les_portal'` | — | API 来源站点 |
| `duration_ms` | INTEGER | `0` | — | 会话总耗时（毫秒） |
| `total_prompt_tokens` | INTEGER | `0` | — | 汇总输入 Token 数 |
| `total_completion_tokens` | INTEGER | `0` | — | 汇总输出 Token 数 |
| `total_tokens` | INTEGER | `0` | — | 汇总总 Token 数 |
| `agent_count` | SMALLINT | `0` | — | 执行的 Agent 数量 |
| `tool_call_count` | SMALLINT | `0` | — | 工具调用总次数 |
| `llm_call_count` | SMALLINT | `0` | — | LLM 调用总次数 |
| `model_name` | VARCHAR(64) | `''` | — | 主模型名称 |
| `selector_model` | VARCHAR(64) | `''` | — | 选择器模型名称 |
| `app_version` | VARCHAR(32) | `''` | — | 应用版本号 |
| `extra` | JSONB | `'{}'` | — | 扩展字段（JSONB），预留后续迭代 |
| `created_at` | TIMESTAMPTZ | `NOW()` | NOT NULL | 创建时间 |
| `updated_at` | TIMESTAMPTZ | `NOW()` | NOT NULL | 最后更新时间 |

**唯一约束**：`UNIQUE(session_id, chat_id)` — 同一会话同一轮次唯一，支持 UPSERT。

#### 索引

```sql
CREATE INDEX IF NOT EXISTS idx_session_user_id     ON session(user_id);
CREATE INDEX IF NOT EXISTS idx_session_status      ON session(status);
CREATE INDEX IF NOT EXISTS idx_session_created_at  ON session(created_at);
CREATE INDEX IF NOT EXISTS idx_session_source_site ON session(source_site);
```

#### status 取值

| 值 | 含义 |
|------|------|
| `running` | 运行中 |
| `completed` | 已完成 |
| `failed` | 失败 |
| `cancelled` | 已取消 |
| `cached` | 缓存命中 |

#### execution_mode 取值

| 值 | 含义 |
|------|------|
| `single_agent` | 单 Agent 直接执行 |
| `full_team` | 完整 PlanAgent + DAG 流水线 |

**用途**：记录 PlanAgent 输出的任务编排方案，便于 DAG 质量回溯与规划重试分析。

| 字段 | 类型 | 默认值 | 约束 | 中文注释 |
|------|------|--------|------|----------|

| `session_id` | VARCHAR(64) | — | NOT NULL, FK | 关联会话 ID |
| `chat_id` | VARCHAR(64) | `''` | FK | 关联对话轮次 ID |

| `is_complete` | BOOLEAN | `FALSE` | — | 是否无需执行任何任务（PlanAgent 直接回答） |
| `duration_ms` | INTEGER | `0` | — | 规划耗时（毫秒） |
| `parse_success` | BOOLEAN | `TRUE` | — | LLM 输出是否解析成功 |


**说明**：`tasks_json` 是完整的 DAG 节点列表，可用于事后重放整个执行计划；`parse_success` + `fallback_used` 用于评估 PlanAgent 输出稳定性。

## 4. 异步写入机制

> 实现文件：`db/writer.py`

### 4.1 设计目标

主流程（Agent 执行、路由、规划）不能因为 DB 写入而阻塞。采用 **生产者-消费者** 模型：业务代码将记录 `enqueue` 到内存队列，后台协程批量消费并写入 PostgreSQL。

### 4.2 DBWriter 类核心结构

```python
class DBWriter:
    def __init__(self) -> None:
        self._queue: asyncio.Queue[_WriteItem | None] = asyncio.Queue(maxsize=10000)
        self._task: asyncio.Task[None] | None = None
        self._running = False
        self._dropped_count = 0
        self._total_enqueued = 0
        self._table_columns: dict[str, set[str]] = {}  # 缓存各表列名
```

### 4.3 队列与批量参数

| 参数 | 值 | 说明 |
|------|------|------|
| `maxsize` | 10000 | 队列最大容量，超出后丢弃并告警 |
| `_FLUSH_INTERVAL` | 0.5 秒 | 队列空闲超过此值即触发一次刷写 |
| `_BATCH_SIZE` | 50 | 队列累计到此条数即触发一次刷写 |

### 4.4 消费循环 `_consume_loop`

后台协程的核心逻辑：

```
循环：
  1. asyncio.wait_for(queue.get(), timeout=0.5s)
       ├── 拿到 item：
       │     ├── 哨兵 None → 刷写剩余 batch 后退出
       │     └── 正常 item → append 到 batch
       │           └── len(batch) >= 50 → 立即 _flush_batch
       └── TimeoutError → 若 batch 非空则 _flush_batch
  2. 异常 → _spill_to_disk（写磁盘 JSONL 兜底，避免丢失）
```

### 4.5 批量写入 `_flush_batch`

#### 4.5.1 按表分组 + FK 排序

```python
_TABLE_ORDER = {
    "session": 0,           # 父表必须最先写
    "routing_decision": 1,
    "dag_plan": 2,
    "agent_execution": 3,
    "tool_call": 4,
    "llm_call": 5,
    "session_feedback": 6,
}
sorted_tables = sorted(by_table.keys(), key=lambda t: _TABLE_ORDER.get(t, 99))
```

**为什么需要 FK 排序**：批次内可能同时包含 session 记录和其子表记录。若先写子表，会因外键约束失败（session 还不存在）。强制 session 表优先写入，再写所有子表。

#### 4.5.2 列过滤 — 防御 schema 漂移

```python
async def _ensure_columns_loaded(self, conn, table) -> None:
    """查询并缓存表的实际列名。"""
    rows = await conn.fetch(
        "SELECT column_name FROM information_schema.columns WHERE table_name = $1",
        table,
    )
    self._table_columns[table] = {r["column_name"] for r in rows}

def _filter_row(self, table, row) -> dict:
    """过滤掉表中不存在的列。"""
    columns = self._table_columns.get(table)
    if not columns:
        return row  # 未缓存时降级为全量写入
    filtered = {k: v for k, v in row.items() if k in columns}
    return filtered
```

**目的**：代码层面新增了字段（如新增 `selector_model`），但生产数据库 schema.sql 还没执行，此时写入会因列不存在而整批失败。列过滤机制会在 INSERT 前丢弃数据库中不存在的列，并打印 warning 日志。

#### 4.5.3 批量 INSERT（executemany）

```python
sql = f"INSERT INTO {table} ({cols_str}) VALUES ({placeholders})"

# session 表使用 UPSERT，避免重复 session_id+chat_id 冲突
if table == "session":
    update_cols = [c for c in columns if c not in ("session_id", "chat_id")]
    update_set = ", ".join(f"{c} = EXCLUDED.{c}" for c in update_cols)
    sql += f" ON CONFLICT (session_id, chat_id) DO UPDATE SET {update_set}"

await conn.executemany(sql, values_list)
```

**关键点**：
- `session` 表使用 `ON CONFLICT (session_id, chat_id) DO UPDATE` 实现 UPSERT，因为 session 会被多次更新（创建时 `running`，完成时 `completed`）
- `update_cols` 仅包含实际传入的列，避免用默认值覆盖已写入的统计字段（这是 `make_session_data(partial=True)` 的配合点）
- 其他子表无 UPSERT，每条记录都是独立的 INSERT

#### 4.5.4 降级路径

```python
try:
    await self._insert_batch(conn, table, rows)
except Exception as e:
    logger.error("批量INSERT失败 %s (%d条): %s", table, len(rows), e)
    # 降级为逐条插入
    for row in rows:
        try:
            await self._insert_one(conn, table, row)
        except Exception as e2:
            logger.error("单条INSERT也失败 %s: %s", table, e2)
```

批量失败时降级为逐条 INSERT，尽最大努力保留数据。

### 4.6 队列溢出处理

```python
async def _enqueue(self, table, data) -> None:
    item = _WriteItem(table, data)
    try:
        self._queue.put_nowait(item)
        self._total_enqueued += 1
    except asyncio.QueueFull:
        self._dropped_count += 1
        logger.warning(
            "[DBWriter] 队列已满，丢弃 %s 记录! dropped=%d/%d",
            table, self._dropped_count, self._total_enqueued + self._dropped_count,
        )
        if self._dropped_count > 100:
            logger.error("[DBWriter] 累计丢弃 %d 条记录，系统可能过载!", self._dropped_count)
```

- 队列满时 `put_nowait` 抛 `QueueFull`，记录丢弃并计数
- 累计丢弃超过 100 条时升级为 ERROR 级别日志，提示系统过载

### 4.7 磁盘兜底 `_spill_to_disk`

```python
def _spill_to_disk(self, batch, error) -> None:
    """将失败的 batch 写入磁盘 JSONL，避免数据丢失。"""
    spill_dir = Path("logs/db_spill")
    spill_path = spill_dir / f"spill_{datetime.now().strftime('%Y%m%d_%H%M%S')}.jsonl"
    with open(spill_path, "w", encoding="utf-8") as f:
        for item in batch:
            f.write(json.dumps({"table": item.table, "data": sanitize_for_json(item.data)},
                               ensure_ascii=False, default=str) + "\n")
```

消费循环异常时，当前 batch 不丢弃，而是写到 `logs/db_spill/spill_YYYYMMDD_HHMMSS.jsonl`，便于事后手动重放。

## 5. 连接池

> 实现文件：`db/pool.py`

### 5.1 连接池参数

```python
_pool = await asyncpg.create_pool(
    dsn=settings.db_dsn,
    min_size=2,            # 最小空闲连接数
    max_size=10,           # 最大连接数
    command_timeout=30,    # 单条 SQL 超时 30 秒
)
```

- `settings.db_dsn` — 从 `config/settings.py` 读取的 `BI_` 前缀环境变量
- `min_size=2` — 平时保持 2 个空闲连接，避免冷启动延迟
- `max_size=10` — 高峰期最多 10 个并发连接，超出后排队
- `command_timeout=30` — 防止慢查询挂起整个写入器

### 5.2 懒初始化 + 双重检查锁

```python
_pool: asyncpg.Pool | None = None
_pool_lock = asyncio.Lock()

async def get_pool() -> asyncpg.Pool:
    global _pool
    if _pool is not None:           # 第一次检查（无锁，快速路径）
        return _pool
    async with _pool_lock:          # 加锁
        if _pool is not None:       # 第二次检查（防止重复创建）
            return _pool
        _pool = await asyncpg.create_pool(...)
    return _pool
```

**为什么需要双重检查**：首次调用 `get_pool()` 时可能有多个协程并发进入，简单锁虽能串行化但每次都要加锁。双重检查让稳态下走无锁快速路径。

### 5.3 连接获取

```python
async with pool.acquire() as conn:
    await conn.execute(sql, *args)
```

`async with pool.acquire()` 是 asyncpg 推荐写法，连接在 `with` 块结束时自动归还连接池，即使发生异常也会释放。

### 5.4 便捷封装

`pool.py` 还提供三个快捷函数，封装 `acquire` 流程：

```python
async def execute(query: str, *args) -> str:
    """执行单条 SQL，返回状态字符串（如 'INSERT 0 1'）。"""

async def fetch(query: str, *args) -> list[asyncpg.Record]:
    """查询多行。"""

async def fetchrow(query: str, *args) -> asyncpg.Record | None:
    """查询单行。"""
```

### 5.5 生命周期

| 时机 | 操作 |
|------|------|
| 应用启动 | `await get_pool()` 懒初始化（首次实际使用时） |
| 应用关闭 | `await close_pool()` 显式关闭，归还所有连接 |

```python

        await _pool.close()
        _pool = None
        logger.info("[DB] 连接池已关闭")
```

### 5.6 init_db 建表入口

```python

    sql = _SCHEMA_PATH.read_text(encoding="utf-8")
```

## 7. 迁移机制

由于本项目未引入独立的 migration 框架（如 Alembic），schema 变更采用 **schema.sql 末尾追加 DO $$ 块** 的幂等方式。

### 7.1 已有迁移示例：`knowledge_meta_count` → `skills_count`

```sql
DO $$
BEGIN
    IF EXISTS (
        SELECT 1 FROM information_schema.columns
        WHERE table_name = 'routing_decision' AND column_name = 'knowledge_meta_count'
    ) THEN
        ALTER TABLE routing_decision RENAME COLUMN knowledge_meta_count TO skills_count;
        COMMENT ON COLUMN routing_decision.skills_count IS 'ES召回的业务技能数量';
    END IF;
END $$;
```

### 7.2 迁移机制要点

| 要点 | 说明 |
|------|------|
| **幂等** | `IF EXISTS ... THEN ... END IF` 包裹，重复执行不会报错 |
| **基于 information_schema** | 通过 `information_schema.columns` 查询当前列状态，避免硬编码版本判断 |
| **保留旧列名识别** | 检查的是**旧列名**（`knowledge_meta_count`）是否存在，若已被重命名为新列名则跳过 |
| **同步更新注释** | `ALTER TABLE ... RENAME COLUMN` 不会自动迁移 `COMMENT ON COLUMN`，需手动重新声明 |
| **追加到 schema.sql 末尾** | 迁移块必须放在所有 CREATE TABLE 之后，否则会因为表不存在而失败 |

### 7.3 后续迁移建议

新增列时推荐模式：

```sql
DO $$
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM information_schema.columns
        WHERE table_name = 'xxx' AND column_name = 'new_column'
    ) THEN
        ALTER TABLE xxx ADD COLUMN new_column VARCHAR(64) DEFAULT '';
        COMMENT ON COLUMN xxx.new_column IS '新列说明';
    END IF;
END $$;
```

**注意**：DBWriter 的列过滤机制（4.5.2 节）保证了代码新增字段时，即使生产数据库尚未执行迁移，也不会因列不存在而整批写入失败 —— 但新数据会丢失该字段，需尽快执行 schema.sql 同步。

```sql
-- 5. 验证外键约束

    kcu.column_name,
    ccu.table_name AS parent_table,
    rc.delete_rule
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.referential_constraints rc ON tc.constraint_name = rc.constraint_name
JOIN information_schema.constraint_column_usage ccu ON rc.unique_constraint_name = ccu.constraint_name
```
